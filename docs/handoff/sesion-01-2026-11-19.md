## 3. Decisiones tomadas (y por qué)

- **Datos a cierre diario, no en vivo.** El sitio trabaja con cierres; refrescar cada pocas horas no aportaba y GitHub Actions `schedule` es «best effort» (se observó que corría ~10 % de lo programado, con demoras de horas). Se pasó de 301 a 53 corridas por semana y el histórico se reescribe entero en cada corrida programada, así que un día salteado se cura solo.
- **Solo se linkea o embebe material de Rockstar; no se aloja nada suyo.** La política de Rockstar permite uso no comercial (sin lucrar ni promocionar un producto o servicio); los links de referido (BingX/Binance) podrían volver comercial al sitio y Take-Two puede pedir baja. Contacto de licencias: `copyright@take2games.com`. El mapa es un link a la página oficial, no una copia.
- **Se borró `cron-worker/`** (Worker disparador): no hacía falta tras pasar a cierre diario.
- **Sin Node/npm en la PC del usuario**, por eso el Worker de analytics no se pudo desplegar desde acá.
- **Arquitectura objetivo (acordada al cierre): híbrido.** Sitio en GitHub Pages; crons y todo el backend en el servidor del usuario (notebook casera con Linux, accesible por SSH). Ver §6.

### 6.2 Arquitectura híbrida

- **GitHub Pages:** solo el sitio estático (como hoy).
- **Servidor casero (notebook con Linux, por SSH):** crons de los cuatro refrescos (`scripts/refresh-*.py`) y cualquier backend que haga falta. Los scripts hacen `git commit` + `git push` al repo, y Pages sigue publicando; si el servidor se cae, el sitio queda online con el último dato.
- A resolver: cron del sistema o timers de systemd; deploy key o token con escritura al repo; **apagar los `schedule` de GitHub Actions** (dejando `workflow_dispatch` como respaldo manual) para no duplicar commits; reintentos y aviso si una corrida falla; si el servidor va a correr también el Worker de analytics o sigue en Cloudflare.
- Si la notebook está en una casa: IP dinámica, cortes de luz/internet y puertos bloqueados por el ISP. Para exponer algo hacia afuera, usar Cloudflare Tunnel; para solo empujar commits no hace falta abrir nada.

## 8. Cómo se trabaja (acuerdos de flujo, confirmados varias veces)

- **Commits:** el usuario dice «Confirma los cambios del árbol de trabajo con un mensaje razonable». Se hace en una **rama nueva** (`git switch -c`), nunca directo en `main`; se agregan los archivos por nombre; mensaje en español y trailer `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>`.
- **Merge:** solo cuando el usuario dice «Sí, mergealo»: `git fetch`, revisar solapamiento con los commits del bot, merge `--ff-only` a `main`, `git push origin main`, y verificar el build de Pages y el sitio en vivo.
- El bot mete commits en `main` todo el tiempo; siempre `fetch` antes de mergear.
- `gh` está autenticado como `LCAITECH` con el scope `workflow`.
- **Entorno:** Windows 11, Git Bash y PowerShell, sin Node. Aparecen avisos de CRLF por `autocrlf` (inocuos). Para probar el sitio: `python -m http.server <puerto>` y abrirlo en el navegador integrado; para probar el Worker sin Node, importar el módulo dinámicamente en el navegador con `env` y requests simulados.
